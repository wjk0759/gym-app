# 05 · AI 设计

## 1. 模型选型（中国大陆）

| 场景 | 首选 | 备选 | 理由 |
|---|---|---|---|
| 计划生成 | DeepSeek-V4.1-Flash-1017 / 通义千问-Plus | 豆包 Pro | 结构化输出稳定、支持思考模式、成本低、已备案 |
| 教练问答 | 通义千问-Plus / DeepSeek | 豆包 | 中文语感好，支持流式 |
| 视觉识别 | 通义千问-VL / 豆包视觉 | GPT-4o（仅海外） | 器械识别需要中文标签与细粒度 |
| 向量 | 通义 text-embedding-v3（1024 维） | BGE-M3 自部署 | 与 pgvector 维度对应 |
| 端上 | Apple Foundation Models（iOS 26+） | — | 免费、隐私好，适合意图分类与摘要 |

**原则：** 只用已完成生成式 AI 备案的模型 API；应用侧仍需做“应用/功能登记”。

## 1.1 AI 私人健身教练

当前只保留一个统一的 **AI 私人健身教练**人设，不再向用户暴露健身教练 / 康复师 / 营养师三个模式。

| 能力 | 范围 | 安全边界 |
|---|---|---|
| 训练 | 计划、动作替代、负荷和恢复安排 | 不做医疗诊断，急性疼痛转诊 |
| 饮食 | 热量、蛋白质、膳食结构和外食选择 | 不做疾病饮食处方，进食障碍/孕期/肾病等转诊 |
| 恢复 | 疼痛分级、红旗症状、恢复期活动 | 不诊断、不给医疗处方，红旗症状要求就医 |

- App 统一调用 `POST /coach/chat` 和 Agent；请求里的 `skill` 字段仅为旧客户端兼容，后端按 `trainer` 统一处理。
- 远程 DeepSeek 只对 Pro 会员开放；未开通或模型失败时回退到本地规则。
- 统一人设 Prompt 位于 `backend/app/prompts/coach_system.md`；旧 `coach_rehab.md` / `coach_nutrition.md` 暂留但不再对外使用。
- AI 调用会写入 `ai_jobs`，后台「AI 使用」查看调用量、延迟、降级和失败。

> 会员校验目前在客户端按 StoreKit 权益执行；生产环境建议增加 Apple 收据/Server Notification 校验，避免直接调用后端绕过会员。

## 2. 计划生成流水线

```
档案 + 目标 + 器械 + 历史
        │
        ▼
  约束编译（规则层，不经过模型）
  ├─ 可用动作候选集（器械 ∩ 无伤病禁忌）
  ├─ 训练分化（1/3/5）＋每周天数（1–7）
  ├─ 每周容量上限
  └─ 单次时长 → 动作数量
        │
        ▼
  Prompt（system + few-shot + 候选动作白名单）
        │
        ▼
  LLM → JSON（response_format=json_object）
        │
        ├─ 解析失败 → 重试 1 次（附错误信息）
        │
        ▼
  校验器
  ├─ 动作必须在白名单
  ├─ 组数 1–6、次数 1–30、休息 0–300
  ├─ 同肌群间隔 ≥48h
  ├─ 周负荷增幅 ≤10%
  └─ 伤病禁忌交集为空
        │
        ├─ 通过 → 写入 programs（version+1）
        └─ 失败 → 规则模板降级（generated_by=template）
```

### 2.1 输出 Schema（节选）

```json
{
  "title": "4 周增肌计划 · 每周 3 练",
  "weeks": 4,
  "days": [
    {
      "week_index": 1,
      "weekday": 1,
      "title": "全身 A",
      "focus": ["legs", "chest", "back"],
      "exercises": [
        {"slug": "goblet_squat", "sets": 4, "reps": "8-10", "weight_kg": 12, "rest_sec": 90, "rpe": 7.5}
      ]
    }
  ]
}
```

完整 schema 约束：

- `days` 长度 = `weekly_days × weeks`
- 每个 `weekday` 在 1–7，且每周不重复
- 每个 day 的 `exercises` 长度 4–7
- 每个 `slug` 必须来自候选白名单
- `title` ≤ 30 字

### 2.2 System Prompt 要点

1. 角色：严谨的体能教练，不做医疗诊断。
2. 只输出 JSON，不输出解释。
3. 只能从给定动作白名单选择，禁止发明动作。
4. 尊重伤病与器械限制；不确定时选择更保守的方案。
5. 渐进超负荷：第 2–4 周重量 +2.5%–5%，或次数 +1–2。
6. 同一肌群 48 小时内不重复大重量训练。

完整模板见 `backend/app/prompts/plan_system.md`。

### 2.3 规则模板降级

即使没有模型，也要能生成可用计划：

- 3 天：全身 A/B/C
- 4 天：上肢 / 下肢 / 上肢 / 下肢
- 5 天：推 / 拉 / 腿 / 上肢 / 下肢
- 动作按“复合 → 孤立”排序
- 组次按目标：减脂 3×12–15、增肌 4×8–10、体能 3×15–20

## 3. 教练记忆

### 3.1 三层结构

| 层 | 内容 | 存储 | 更新时机 |
|---|---|---|---|
| 档案层 | 目标、伤病、器械、偏好 | `profiles` / `goals` | 用户修改时 |
| 摘要层 | 每 4 次训练的完成率、容量趋势、主观疲劳 | `ai_memories(kind=summary)` | 每 4 次训练 |
| 检索层 | 具体反馈、动作问题 | `ai_memories` + embedding | 对话/反馈时 |

### 3.2 上下文组装（控制 token）

```
system prompt（安全 + 角色）
+ 用户档案（结构化，<300 token）
+ 当前计划（只取今天 ± 下一次，<500 token）
+ 最近 4 次训练摘要（<300 token）
+ 检索到的 3 条记忆（<300 token）
+ 最近 6 轮对话
+ 本轮问题
```

绝不把完整训练历史塞进上下文。

### 3.3 调整规则（确定性，优先于模型）

| 信号 | 动作 |
|---|---|
| 周完成率 <60% | 总组数 −20%，优先删孤立动作 |
| 连续 2 次 RPE ≥9 | 主项重量 −5%–10% |
| 连续 2 周同动作无进步 | 换变式或调整次数区间 |
| 停练 ≥2 周 | 负荷回到 80%，第一周不冲重量 |
| 用户连续拒绝某动作 2 次 | 加入偏好黑名单，生成时降权 |

模型负责写“调整理由”和微调编排，不负责决定是否减量。

## 4. 器械识别

```
拍照 → 压缩到 1280px → 上传 OSS（签名直传）
     → 视觉模型（结构化输出：器械名、置信度、可见特征）
     → 与自建器械库做字符串/向量匹配
     → Top 3 候选 + 对应动作 + 视频
     → 置信度 <0.6 或候选冲突 → 用户确认
```

**关键设计：**

- 视觉模型只负责“看出是什么器械”，**动作映射查表**，不让模型自由发挥。
- 器械库字段：`slug`、中文名、别名、目标肌群、替代动作、视频 ID、常见误识别。
- 识别失败必须有手动搜索入口，这是可用性底线。
- 用户纠正结果写入 `equipment_scans.result`，作为后续微调数据。

**不建议 P0 自训练分类器。** 先用多模态模型 + 规则匹配验证需求，积累 5000 张真实图片后再考虑蒸馏。

## 5. 教练问答

### 5.1 RAG 知识库

| 来源 | 内容 | 更新 |
|---|---|---|
| 动作库 | 要领、常见错误、替代动作 | 随动作库 |
| 运动解剖 | 肌群、关节动作 | 一次性构建 |
| FAQ | 训练频率、酸痛、平台期、经期训练 | 每月 |
| 安全规则 | 红旗症状、就医指引 | 法务审核后固定 |

### 5.2 安全策略（硬编码，不依赖模型）

命中以下任一，直接返回兜底话术并标记 `safety_flag=medical_referral`：

- 胸痛、胸闷、晕厥、呼吸困难
- 关节剧痛、肿胀、无法承重、麻木
- 怀孕、产后 6 周内、术后恢复期
- 未成年人 + 减重/增肌补剂
- 进食障碍相关表述

兜底话术示例：

> 你描述的情况不适合继续按计划训练。请先停止训练并咨询医生或康复师；如果你愿意，我可以帮你把今天的训练改成低强度恢复内容。

### 5.3 防幻觉

- 回答中提到的动作必须在动作库中存在，否则客户端不渲染动作卡片。
- 不让模型给具体药物、补剂剂量。
- 不让模型计算疾病相关的热量/蛋白处方。

## 6. 饮食与外卖（P1/P2）

### 6.1 热量计算

- Mifflin-St Jeor 计算 BMR
- 活动系数 1.2 / 1.375 / 1.55 / 1.725
- 目标调整：减脂 −15%，增肌 +10%
- 蛋白质 1.6–2.2g/kg，脂肪 0.8–1g/kg，剩余给碳水
- 结果给出区间，不给单点精确值

### 6.2 外卖的现实约束

美团联盟提供的是**活动/红包/会场推广链接**，不提供：

- 按营养条件搜索附近菜品
- 商家菜单与配料表
- 菜品热量数据

因此：

1. P1 只做“饮食计划 + 手动记录 + 自建食物库”
2. P2 才做外卖跳转，且只承诺“帮你打开美团搜索/活动页”，不承诺营养匹配
3. 若未来拿到美团开放平台服务商资质，再考虑真实菜品数据
4. UI 上必须标注“营养信息以商家页面为准”，避免误导

## 7. 成本控制

| 手段 | 效果 |
|---|---|
| 计划生成结果缓存 24h | 避免重复生成 |
| 对话只带最近 6 轮 | 控制输入 token |
| 摘要异步生成 | 用便宜模型 |
| 视觉图片压缩到 1280px | 降低视觉 token |
| 失败降级模板 | 不产生重试费用 |
| 按用户日配额 | 防刷 |

粗估：1000 DAU、人均每天 3 次 AI 调用，月成本约 1,500–4,000 元（视模型与上下文长度）。
