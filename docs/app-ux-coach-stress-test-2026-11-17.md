## 三、P0：新装登录已有账号被强制重新建档

### 复现

1. 删除 App 后重新安装（本地无 `fitai-state.json`）。
2. 用已有账号 `macqa_coach` 走“账号密码”登录。
3. 服务端登录返回 `onboarding_required=false`，`/me` 返回 `profile.onboarded=true`。
4. App 没有进入主界面，而是显示：

```text
告诉我你的情况，
我帮你生成起点报告
[开始] [退出登录]
```

等待 20 秒仍无 Tab Bar。

5. 继续点“开始”走完 onboarding（使用默认值）后，服务端资料被覆盖：

```text
修改前：31 岁，体脂 18%，目标 76kg → 78kg
修改后：30 岁，体脂 22.5%，目标 75kg，目标日期 2027-02-17
```

### 影响

- 老用户换机 / 重装 / TestFlight 审核账号登录后会被当成新用户。
- 用户按引导重填默认值后，服务端真实档案、目标、身体数据被覆盖，属于数据丢失。
- 用户只能退出登录，无法跳过。

### 根因

`RootView` 的分流条件是本地 `store.profile.isOnboarded`：

```swift
} else if store.profile.isOnboarded || qaBypassAuth {
    MainTabView()
} else {
    CoachOnboardingView()
}
```

`AuthStore.loginWithPassword` 只保存 token 和 `onboardingRequired`，`AuthResponse` 不解析 `profile`；`AppStore.switchUser` 只 `load()` 本地文件，服务端 `/me` 是异步 `syncPendingUserData()` 里才拉取。首屏渲染时本地 profile 还是空，所以直接进了 onboarding。等 `/me` 回来也不会自动离开 onboarding，因为本地 `profile.isOnboarded` 已被 onboarding 流程接管。

### 建议修复

- 登录成功后先拉 `/me`（或让 `AuthResponse` 带上 profile）再决定显示登录后页面。
- 分流使用 `auth.onboardingRequired` 或“服务端档案已加载”状态，不要只看本地 `store.profile.isOnboarded`。
- Onboarding 增加“我已有档案，跳过”兜底；不要默认覆盖已有 `nickname/birth_date/body_fat/goal`。
- 回归：删除 App → 登录已有账号 → 直接进主界面；服务端资料不变。

## 四、P1：计划生成不遵守器械，静默丢训练日

### 复现

1. 把通用器械改成只有徒手：

```http
PUT /api/v1/equipment/universal
{"enabled_slugs":["bodyweight"]}
```

2. `GET /api/v1/equipment/universal` 返回只有徒手，但 `GET /api/v1/me` 的 `profile.equipment` 仍返回：

```json
["bodyweight", "dumbbell"]
```

3. `POST /api/v1/plans/generate {"force":true}` 返回的计划标题是“每周 3 练”，但：

```text
days.length = 4        // 只有 4 天，每周 1 练
weekday = [1,1,1,1]    // 全是周一
```

warnings：

```text
高位下拉 需要 machine，已移除
杠铃臀推 需要 barbell，已移除
坐姿划船 需要 machine，已移除
第 1 周星期 3 有效动作不足 3 个，已跳过
腿举 需要 machine，已移除
弹力绳-俯身划船 需要 band，已移除
第 1 周星期 5 有效动作不足 3 个，已跳过
...
```

计划里仍然包含哑铃动作：

```text
goblet_squat
vital-dumbbell-bench-press
```

4. 同一账号只选徒手时，另一次生成直接返回：

```json
{"error":{"code":"UNSAFE_PLAN","message":"以你当前的伤病和器械条件，无法生成安全计划。请补充可用器械，或先咨询教练 / 康复师。"}}
```

5. 把通用器械恢复为徒手+哑铃后，生成恢复正常：

```text
days.length = 12
weekday = {1: 4, 3: 4, 5: 4}
warnings = []
```

### 影响

- 用户取消哑铃后，计划仍然安排哑铃；没有器械的人无法完成计划。
- 计划标题写“每周 3 练”，实际只有 1 练，且周三、周五被静默跳过。
- 部分账号直接无法生成计划，错误文案把原因归为“伤病/器械条件”。

### 根因方向

- `replace_universal_equipment` 后 `profile.equipment` 仍通过 `_legacy_types()` 合并旧 profile 器械，缓存不会删除已取消的器械。
- `user_plan_pool_slugs` 在“只有徒手”时返回空池，`_allowed_exercises` 回退到全部 `plan_eligible`，prompt 把 machine/barbell/band 都当成可用；validator 再按 `profile.equipment` 删除，导致训练日动作不足。
- `validate_plan` 对不足 3 个动作的训练日直接 `continue`，没有从可用池补齐，也没有让整个生成失败。

### 建议修复

- `profile.equipment` 只从当前 inventory 派生；取消器械时同步移除，不再合并旧值。
- 空池时按 `profile.equipment` 过滤，不要把全库动作塞给模型。
- 模型返回后按“可用动作池”补齐不足 3 个的训练日；补不齐就明确失败，不要静默跳过。
- 生成结果强校验 `days.count == weekly_days * weeks` 和动作 `equipment`，不符合直接报错。
- 回归：徒手-only 账号生成 3 练/周计划，动作全部是徒手；取消哑铃后计划不再出现哑铃。

## 五、P1：多食物份量丢失

### 复现

对同一账号发送：

```text
午餐吃了 100g 鸡胸肉和 250g 米饭
```

返回的 `log_food` 卡：

```json
{
  "items": [
    {"name": "鸡胸肉", "portion": "100g", "grams": 100.0},
    {"name": "米饭", "portion": "约150g", "grams": 150.0}
  ]
}
```

执行后写入的饮食记录也是米饭 150g。

其他样本：

```text
"午餐吃了 100g 米饭和 250g 牛肉"
→ 牛肉 120g（不是 250g）

"午餐吃了 200g 米饭和 150g 鸡胸肉"
→ 米饭 200g、鸡胸肉 150g（正确）

"午餐吃了 300g 米饭"
→ 米饭 300g（正确）

"午餐吃了 100g 鸡胸肉、150g 米饭和 200g 西兰花"
→ 100/150/200（正确）
```

### 影响

- 第二种食物经常使用默认份量，热量和宏量营养素全部偏低。
- 用户确认的是错误数据，后续周报、目标、教练建议都会基于错误记录。
- 这是数据正确性问题，不是文案问题。

### 建议修复

- 食物解析按 item 保留显式 `grams/portion`，不要用默认值覆盖。
- 对“食物 A + 食物 B”分别校验数量；解析不到时追问，不要静默填默认。
- 加回归：两种食物、顺序对调、三种食物、中文数字/毫升/个。

## 六、P1：待确认卡份量修正失败

### 复现

1. 先产生一张待确认的饮食卡：

```text
午餐吃了 100g 鸡胸肉和 200g 米饭
```

2. 同一会话发送：

```text
米饭改成 250g
```

实际回复：

```text
还有几项需要确认：
· 250g 指的是哪种食物？缺少食物名称。
· 「250g」我还不认识，能告诉我它的热量/蛋白质，或者说它像什么食物吗？
```

没有生成修正卡。

3. 改成：

```text
米饭 250g
```

回复“改好了，确认后按新的份量写入”，并生成米饭 250g 的修正卡。

### 根因

`_pending_food_replacement()` 先于 `_pending_action_correction()` 执行。“米饭改成 250g”被正则识别为“把米饭换成 250g”，于是把“250g”当成新食物名去解析，失败后返回缺食物名称的问题，永远走不到纯份量修正的快路径。

### 建议修复

- 先判断 `new_text` 是否只是数量（`250g / 250克 / 半碗`）；是数量则直接走 `_pending_action_correction`。
- 只有 `new_text` 含新食物名时才走替换解析。
- 回归：`改成 250g`、`换成 250 克`、`米饭 250g` 三种说法都生成同一张修正卡。

## 七、P1：训练补录生成不存在的动作 slug

### 复现

发送：

```text
刚练完深蹲 4组10次 60kg
```

生成动作卡：

```json
{
  "type": "log_workout",
  "payload": {
    "sets": [
      {"slug": "barbell-full-squat", "set_index": null, "weight_kg": 60, "reps": 10}
    ]
  }
}
```

执行：

```http
POST /api/v1/agent/actions/{id}/run
```

返回：

```json
{"error":{"code":"VALIDATION_ERROR","message":"动作不存在：barbell-full-squat"}}
```

App 侧把 422 映射为：

```text
训练记录失败：参数不合法
```

### 影响

- 教练说“记录卡准备好了”，用户确认后失败，训练记录丢失。
- 用户看不到具体原因（动作不存在），无法自救。
- 用户器械只有徒手/哑铃，动作却选了 barbell。

### 建议修复

- 生成 `log_workout` 前用 `lookup_exercise` 或本地动作库校验 slug，使用真实 slug（如 `vital-*`）。
- 校验动作 `equipment` 是否在用户可用器械内；没有就换动作或追问。
- 服务端 422 返回具体字段/动作名，App 显示可读错误。
- 回归：徒手/哑铃用户补录深蹲、卧推、跑步，确认后能写入训练历史。

## 八、P1：多意图只执行一个，且日期/餐次写错

### 复现

发送：

```text
今天训练改到明天，再记 200g 米饭
```

返回只有一个动作：

```json
{
  "type": "log_food",
  "payload": {
    "date": "2026-11-18",
    "meal": "snack",
    "items": [{"name": "米饭", "grams": 200}]
  }
}
```

- “训练改到明天”完全丢失，没有 `reschedule_training`。
- 米饭被记到明天（11-18）的加餐，而不是今天。
- 回复只说“已识别 1 种食物”，没有指出只完成了一半。

### 影响

- 用户以为两件事都办了，实际训练没改、饮食记错天。
- 多意图在真实用户里很常见（“改计划 + 记饮食”“记体重 + 换餐”）。

### 建议修复

- 解析出多个 intent 时，要么生成多个动作（受 `MAX_APP_ACTIONS=7` 限制），要么明确追问“先办哪件”。
- 饮食日期不要继承“训练改到明天”的日期；没有明确日期时默认今天。
- 没有明确餐次时追问，或按当前时间用 `MealType.suggested()`，不要默认 snack。
- 回复必须说明实际执行了几个意图。

## 九、P2：回复承诺动作卡但实际没有

### 复现

第一次发送：

```text
刚跑了 5 公里，30 分钟
```

回复：

```text
...记录卡已经准备好了，你确认后就会写入。
```

实际：

```text
status = completed
actions = []
pending_draft = null
```

同样输入第二次才生成 `log_workout` 动作。说明模型/工具链存在概率性漏动作。

### 影响

用户找不到确认卡，以为 App 卡住；或者反复发消息造成重复记录。

### 建议修复

- 回复生成后做一致性校验：如果回复包含“记录卡/操作卡/确认后”，必须至少有一个 action 或 pending_draft；否则改写文案或重试。
- 对 `log_workout`、`log_food`、`update_goal` 等写操作强制要求动作，不允许只回复。

## 十、P2：确认前使用“记上了/记好了”

### 复现

身体数据：

```text
今天体重 71.2kg，体脂 17.6%
```

回复：

```text
记上了：71.2kg、17.6%...点确认就写进今天。
```

状态是 `needs_confirmation`，尚未写入。

饮食：

```text
米饭 200g
```

回复：

```text
米饭 200g 记好了...点确认记进饮食页。
```

### 影响

用户可能以为已经保存，直接退出；实际数据没写入。

### 建议修复

- 确认前统一用“已准备好 / 确认后写入”，不要用完成时。
- 写入成功后用“已记录”并展示结果。

## 十一、P2：自然语言跳过不生成动作

### 复现

```text
明天我不练了，跳过全身 B
→ actions = []
→ 回复：你是想直接跳过，还是挪到周四补上？

明天全身 B 不练了
→ actions = []

把明天全身 B 跳过
→ skip_training action（正确）
```

### 影响

用户已经明确说“跳过/不练了”，仍要多一轮确认；容易放弃或误以为已跳过。

### 建议修复

- 识别“跳过/不练了/休息” + 明确日期/day title 时直接生成 skip 卡。
- 只有日期或 day 不明确时才追问。

## 十二、P2：长期记忆写入未确认动作，且内容错误

### 复现

- 发送“我改主意了，还是增肌，目标 78kg”，生成 `update_goal` 卡但**未确认**。
- `/agent/memories` 已出现：

```text
用户训练目标为增肌，目标体重 78kg
```

而 `/me` 的 goal 仍是 76kg。

- 记忆里还有：

```text
用户当前训练计划采用全身 A 与全身 B 交替安排
```

实际计划是全身 A / B / C 三天循环。

### 影响

- 用户放弃确认后，教练仍按 78kg 回答，目标冲突。
- 错误记忆会持续污染后续计划、饮食和复盘。

### 建议修复

- 只从已执行/已确认的动作写记忆；pending 卡不写。
- 记忆写入前与当前 plan/profile 校验；计划标题/天数不一致时不写。
- 提供记忆纠错/删除入口。

## 十三、P2：删除记忆死路

### 复现

```text
忘掉我不喜欢跑步这条
→ 这条我删不掉，但记下了：以后不按“你讨厌跑步”来排有氧。
```

App 内有“我的 → AI 长期记忆”页面，但教练没有给出入口或动作。

### 建议修复

- 增加 `forget_memory` 工具，或在回复里给“打开长期记忆”的操作卡/深链。
- 不要简单回复“删不掉”。

## 十四、已通过的能力

- F1 布局回归：iPhone 17 / SE 首屏快捷卡不被 Tab Bar 覆盖；二级页隐藏 Tab Bar；返回恢复。
- Onboarding：8 步可走通，报告页和计划生成可完成。
- 计划生成（器械池正确时）：4 周 × 3 练 = 12 天，无 warning。
- 饮食计划：明确“没有忌口 + 高蛋白”后生成 `create_diet_plan` 卡。
- 饮食记录执行 + 撤销：写入两条、撤销后清空。
- 安全：胸痛停止训练/就医；膝盖疼避免大重量；不承诺“一个月瘦 20 斤”；拒绝过度训练。
- 拒答：system prompt 注入、写代码等离题请求均拒绝。
- 记忆：花生过敏记忆 + 后续“花生酱能吃吗”正确回答。
- 会话隔离：新会话不知道上一会话内容。
- 回归：`FitAITests` 121/121、`FitAIUITests` 6/6。
